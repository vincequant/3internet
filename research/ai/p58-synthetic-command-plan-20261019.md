# P58 合成命令（無勢力視角派單）研究計劃 — 2026-10-19

## 需求

不使用遊戲界面，在**無勢力視角**下，把「練兵／訓練」這類命令送進指令流通道，
讓主機與其他客戶端真的套用（例如：替某勢力訓練鐵騎）。

## 已確認的事實

### 1) 訓練命令的線路格式（wire）＝內政指令 kind 18

來源：`bridge/native_command_evidence.py`（實錄 95 條指令解碼時的同一份佈局）

```
body = [13 bytes 基底][actor_force_id:i32][parameter:i32][value:i32][extra:i32]
parameter: 0=步兵訓練 1=騎兵訓練 2=弓兵訓練
subtype  : 0=訓練（同一 kind 的其它 subtype：2 施捨、3 米交易、4 建設、5 拆除、8 偵察）
```

也就是說「替 X 勢力訓練鐵騎 N 人」＝ `actor=X, parameter=1, value=N, extra=?`。

### 2) 介面按「練兵」時，遊戲內部做了什麼（反組譯 `0x4A3BA8`）

```
push 0x44 ; call 0x4D1D22        ; operator new(0x44)
call 0x485256                   ; ctor：vtable=0x50A4F8、+0x38=-1、+0x3C=0、+0x40=0
call 0x4852A6(obj, v1, v2, 0x12C/0x12D/0x12E)  ; 填值 + 虛呼叫 [vtable+0x78]
call 0x4B08B4(container=[dialog+0x100], obj, 0) ; 交給遊戲自己的佇列
```
→ 命令物件是**同一族 0x44 bytes、vtable 0x50A4F8** 的類別，最後一步是把物件塞進
遊戲自己的佇列（不是自己組封包）。

### 3) 自己造封包寄出＝失敗（已實測）

P57 E1：用可靠通道 `0x4C80→0x4B60` 送 71B「出征」命令 → 主機收到（我方序號推進）
但**沒進批次**、玩家端數值不變。E3 改寄件人也無效。
→ 結論：**必須走遊戲自家的命令物件＋佇列**，不能在傳輸層硬塞。

### 4) 我們目前的 suppress 補丁只擋「同步控制幀」，不擋命令

`SUPPRESS_PATCHES` 實為 Koeinm 的兩個小上行（4B / 8B 控制幀：0x100024F0、0x10002530），
兩者都會 `0x4C80(入隊) → 0x4B60(提交)`。命令批次的實際上行路徑另有一條。
→ 所以「命令送不出去」不能只怪 suppress，需在下一局用主機批次證據判斷。

## 待確認（決定整條路線是否成立）

1. **藏身＋無勢力的風夜，送出的命令主機收不收？**
   - 正面證據：2026-10-18 15:4x（在風夜客戶端下指令 → 真風雲數值同步變化）。
   - 反面證據：P57 E1（傳輸層硬塞被忽略）。
   - 判定方法：一次介面點擊，看主機批次是否出現該記錄、其他客戶端數值是否變。
2. 命令的 `actor_force_id` 是否就是「假裝的勢力」——若主機不校驗發送者身分（P46 假說），
   填哪個勢力就套用到哪個勢力。
3. `extra` 欄位語義（訓練命令的第 4 個 int）未知，需從實錄比對（同一城池連兩次訓練的差分）。

## 實驗階梯（每步一發、可逆）

- **L0（無害）**：新局，風夜 slot=空席（無勢力視角），**介面**按一次練兵；
  看主機 control5 批次是否含 kind18 記錄、丁滿／風雲數值是否變。
  → 這一步同時回答「無勢力視角下命令能不能生效」與「今天卡死是不是命令沒出去」。
- **L1**：若 L0 成立 → 做「合成命令」agent：造同型別命令物件 → 呼叫 `0x4B08B4` 類的入列
  （或直接呼叫 `0x4A3BA8` 的內部建構段）→ 一次一發，驗主機批次。
- **L2**：包成 Hub 按鈕「下達練兵：騎兵 ×N（指定勢力）」。
- **L3（破壞性）**：才談其他屬性修改；逐次報批。

## 風險

- 合成命令若少了 UI 端的「等待回合」流程，理論上不會卡；但主機若因「發送者不在同步名單」
  而忽略，命令就變成靜默失敗（可從主機批次直接看出，不需要重開局）。
- 訓練命令的 `value` 上限未知，先小額（例如 100）驗證，再放大。
